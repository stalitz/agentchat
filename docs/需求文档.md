# 需求文档 · Agent CLI Orchestrator

> 项目目标：把 Claude Code / Codex 两个 CLI agent 当作「黑盒子进程」编排起来，
> 让它们就同一项目的设计 + 代码实现进行多轮讨论、互相续写、收敛共识，
> 并以 Web 看板呈现过程，支持人工打断与共享记忆。

## 1. 背景与定位

- 用户希望用**不同模型/外壳**的多个 agent 协作，对同一项目经过多轮讨论达成共识。
- 架构要点：**共享项目工作区（磁盘）为单一事实源**，agent 按需读取片段，编排层完全掌控上下文（只喂「对手最新一轮 + 记忆摘要 + 角色」），避免上下文隐性膨胀。
- 共识产物沉淀到项目目录下的 `.agentchat/sessions.json`（每条会话含 `messages` + `memory`）；公共记忆可续，且**按会话隔离**。
- 一个项目可开**多条会话**，各自独立历史与记忆，互不串场。

## 2. 角色与用户

| 角色 | 说明 |
|------|------|
| 编排者（Orchestrator） | 本系统：轮流调度 agent、构造 prompt、广播事件、管理记忆与终止。 |
| Agent（架构师/实现者） | 被编排的 CLI 子进程：Claude Code、Codex，或调试用的 Fake agent。 |
| 人类观察者/介入者 | 通过 Web 看板查看对话流、切换/新建会话、暂停/停止/注入消息。 |

## 3. 功能需求

### FR1 配置管理（三层作用域）
配置分三个作用域，互不越界：
- **Agent 级**：名称、类型、角色 prompt、模型、CLI 参数、**模型网关接入 `base_url` / `api_key`**、**「思考」开关 `think`（覆盖全局，见 FR1.1）**（`AgentConfig` 字段）。
- **会话级**：一场讨论的轮次上限 `max_rounds`——发起讨论时经 WebSocket `start` 传入，所有 agent 共用同一上限，不挂在 Agent 上（避免「短板 agent 的配置锁死整场」）。**另含「思考」开关（见 FR1.1）**：每场讨论可独立开/关模型思考过程，按会话生效且**优先级最高**（覆盖 agent 级与全局）。
- **App 级（全局设置）**：存于 `config.json` 顶层 `settings`，对所有讨论统一生效，改完即时生效无需重启：
  - 单轮静默超时 `default_timeout`。
  - **辩论模式默认轮次上限 `default_max_rounds`**：作为「发起讨论时轮次输入框」的默认值来源——用户在 composer 没手动改过时，轮次框预填此值；后端 `start` 也以它为兜底默认值。从而「最大轮次的默认值」从全局设置统一管控，而非前端硬编码 12。
  - **Claude 输出上限 `claude_max_output_tokens`**（默认 64000）：claude 子进程单次响应 output token 上限；推理模型思考块长/输出大时可调大防报错。
  - **思考总开关 `think`**（默认开，App 级**全局默认**，作用于**全部 agent**）：作为三级开关的兜底默认（见 FR1.1）。关掉后各后端尽力关闭思考生成——Ollama 经内置网关带 `think:false`（gemma 等推理模型不再产思考块，输出量骤降）；codex 降 `model_reasoning_effort`；真实 claude 直连无干净开关（Claude Code CLI 无 `--think`，仅经网关的 Ollama 生效）。
  - **通用辩论提示词模板 `prompt_templates.debate.<slot>`**：8 个槽位（consensus/floor_notice/rejected_inject/peer_rejected/proposal_peer/proposal_self/proposal_none/extra_rules）可配置覆盖，缺省用内置默认；**全局设置界面显示当前生效文本（含默认），可改写、可一键「恢复默认」**（与默认一致即视为未配置）；会话启动时读快照，改配置对新会话生效。`extra_rules` 为每轮常驻的附加规则（默认空，盲棋/游戏等场景专属规则放这）。

### FR1.1 「思考」开关（三级作用域：会话 > agent > 全局；已实现 2026-09-14）
- **演进诉求**：最初它只是 App 级全局 `ollama_think`，且实现上**只作用于「claude-code + base_url 指向本网关 → Ollama」一条路径**。用户质疑三点：「全局不应该是限制全部 agent 的吗？要限制某个 agent 应在对应 agent 上设置」「为什么是 ollama 不是 claude」「codex 不能限制吗」。故重构为**三级开关**并逐后端补齐。
- **三级作用域与优先级（Session > Agent > App）**：`store.resolve_think(agent, session, settings)` 统一解析——会话级 `sessions.json.think` 优先；否则 agent 级 `AgentConfig.think`（`None`=继承）；否则全局 `settings.think`。编排层 `Session.__init__` 按 agent 各解析一次（`think_by_agent`），同时用于注入网关 URL 与传给 `AgentRuntime`。
- **UI 三处**：① 全局设置（⚙ 设置 →「思考（全局）」勾选框 → `settings.think`，**作用全部 agent**）；② agent 表单（「思考（本 agent）」三态：继承全局/开/关 → `AgentConfig.think`）；③ 会话头部「💡 思考」（→ `sessions.json.think`，**优先级最高**）。
- **逐后端落地（诚实边界：三个后端没有统一的「关思考」开关）**：
  - **Ollama（经内置网关）**：生效值 False → 请求带 `think:false`（gemma 等推理模型不再产思考块；实测输出从单轮数万 token 降到个位数）。**完全生效**。
  - **codex**：生效值 False → 注入 `-c model_reasoning_effort="low"`（app-server 与 exec 两条路径都注入）。codex 无 `--think` 开关，只能经 `-c` 覆盖（不动用户 `~/.codex/config.toml`）。**best-effort**：provider/模型不支持 reasoning effort 时可能无实际效果（已实测 codex-cli 0.146.1 接受该值、正常启动）。
  - **真实 claude 直连**：**无干净开关**——Claude Code CLI 没有 `--think/--no-think`（`claude --help` 实测无此 flag），思考由模型本身决定。故该开关对真实 claude（不经网关）不生效，属**已知限制**（不是「不能做」，而是 CLI 未暴露）。
- **网关如何拿到生效值（含 agent 维度）**：会话/agent 两维只有编排层知道，网关是无状态 HTTP 端点、只知道 `pid/sid`。故编排层把算好的生效值编进 claude 的 `ANTHROPIC_BASE_URL` **路径**：对指向本服务的 `base_url` 注入 `/gw/<pid>/<sid>/think/<0|1>`（`orchestrator.Session._gw_url`）；claude 发请求即命中 `POST /gw/{pid}/{sid}/think/{flag}/v1/messages`，网关直接采用该 flag（`think_override`）。**必须用路径段而非 `?query`**：claude 以 `base_url + "/v1/messages"` 字符串拼接，`base_url` 带 query 会被拼坏（→ `...?think=0/v1/messages`）；另保留无 think 段的旧路由（网关按 会话>全局 自解析，无 agent 维度）。
- **隔离配置目录同步**：claude 2.x 会把隔离配置目录 `settings.json` 的 `env.ANTHROPIC_BASE_URL` 合并并**覆盖**子进程 env，故编排层在每次拉起子进程前把当前 base_url（含 `/think/<0|1>`）同步写进该文件（`_sync_claude_base_url` + `_claude_config_dir`），否则开关退化为全局。
- **工具往返兼容**：claude 把 `tool_result` 回传的 URL 编码进 path（如 `/http%3A//127.0.0.1%3A8777/gw/<pid>/<sid>/think/0/v1/messages?beta=true`），`_rewrite_claude_tool_roundtrip_url` 中间件用 `urlparse` 提取 path（保留含 `/think/<0|1>` 的 `/gw/...` 前缀）再改写，路径不丢。
- **兼容旧数据**：读 `settings` 与 `sessions.json` 时兼容 #104 旧字段 `ollama_think`（旧 `config.json` 只写了它，改名前用户的 `false` 仍生效）；写入统一用 `think`。
- **命名修正**：原 `ollama_think` 会把「仅 Ollama 生效」的实现细节误表为全局语义，故更名 `think`（全局=全部 agent）。

可增删改 **Agent / Team（一组 Agent）/ Project（名称、项目目录、关联 Team）**，持久化到 `data/config.json`（JSON 文件，零数据库）。

> 运行目录不在 Agent 上——agent 跟随其所属项目的目录运行（会话以项目目录为 `cwd` 启动 CLI）。

### FR2 Agent 类型
- `claude-code`：调用 `claude --output-format stream-json --input-format stream-json --verbose --dangerously-skip-permissions`（prompt 经 stdin 以 user 帧传入；首轮 `--session-id <uuid>`，续接连 `--resume <id>`）。
- `codex`：**优先 `codex app-server` 真流式**（JSON-RPC over stdio，逐 delta 增量推文本与思考），握手/启动失败自动回退 `codex exec --json`（兜底，见 §6 第 9 条 + FR12）。app-server 命令：`codex app-server --listen stdio:// [-c mcp_servers.terminate-signal.*...] [-c model='<model>'] [-c model_reasoning_effort="low"]`（注意：app-server **不接受 `-m`** 与 `--skip-git-repo-check`，模型经 `-c model='...'` 覆盖、thread/start 非 git/未受信目录实测可直接成功）；`-c` 注入 `terminate-signal` MCP 服务以提供 `end_discussion` 工具（理由见 FR5.3a 末条）；**三级「思考」开关生效值 False 时注入 `-c model_reasoning_effort="low"`（best-effort，见 FR1.1）**。兜底 exec 命令：`codex exec --json --skip-git-repo-check [-c <MCP 注入>...] [-c model_reasoning_effort="low"] [-m <model>] [resume <id>] "<prompt>"`。**agent 配了 `base_url` 时，两条命令都额外注入 provider 覆盖**（`-c model_provider="ollama"` 或自定义 `agentchat`，一律命令行 `-c`、不动 `~/.codex/config.toml`，见 FR13）。
- `fake`：**调试专用假 agent**，纯内存流式吐确定性文本，不调用任何 CLI、不烧模型 token。

### FR3 会话编排（两种模式，按 Team 内 agent 数自动切换）

| | **对话模式 chat（单 agent）** | **辩论模式 debate（≥2 agent）** |
|---|---|---|
| 触发 | Team 只有 1 个 agent | Team 有 ≥2 个 agent |
| 语义 | 人机一问一答，可无限续；一次「发送」= 用户一条 + agent 一条 | agent 轮流发言（round-robin），跑到上限/收敛/手动停 |
| 轮次 `max_rounds` | 不适用（置灰） | 生效 |
| 暂停 / 继续 / 停止 / 人工介入 | 不适用（隐藏，点了后端回错误提示） | 适用 |
| 收敛（agent 主动结束讨论） | 不适用（prompt 明确要求不调用工具） | 适用（`end_discussion` 工具调用：最小轮数 gate + 两阶段确认，见 FR5.3a；TERMINATE 关键词降级兜底） |
| 主按钮 | 「发送」 | 「开始讨论」/「继续讨论（已有 N 条）」 |

- **用户消息本身也是会话的一部分**：任务 / 对话输入 / 人工介入都以 `speaker="human"` 落库并回显（`role` 区分「用户」/「任务」/「人工介入」），刷新后能看到自己说过什么。
- 每轮 prompt（状态式 delta 路由）：对话模式 = 身份行 + 用户本轮新消息（delta）；辩论模式 = 身份行 + 对手上一句（delta）+ （可选）人工注入 / 新议题。**不再每轮重搬整段历史**——各 agent 在自身持续 CLI 会话里持有完整上下文（app↔agent 1:1 持续会话，见 FR6），token 极省。
- 流式转发 token 到前端（WebSocket）；一次运行结束广播 `run_end{mode}`，前端据此恢复按钮并刷新会话列表。
- **续接「继续」按钮（resume）必须标记会话在跑**：`ctrl('resume')` 点击后立即置 `runningBySid[sid]=true`（与 `startSession` 一致），且 `turn_start` 事件也置位。否则 `run_end` 的 250ms 重载守卫（`if (runningBySid[curSid]) return`）对续接路径永远失效——续接首个 agent 刚流式渲染的内容会被重载抹掉（g1 输出消失、刷新才见；象棋g+ / 五子棋续接均实测）。`run_end` 后仍复位为 false 以恢复按钮。
- **`turn_start` 必须复位上一轮流式游标（cur/curThinking/curAnswer…）**：气泡懒建依赖每轮 `cur` 为 null。若上一轮因被打断 / 报错未发 `turn_end`（如实测 g2 流式中被介入打断），`cur` 仍指向旧气泡，下一轮首个 thinking/token 会被 append 进旧气泡造成跨轮污染（g1 内容合并进 g2 气泡）。故 `turn_start` 内先 `hideLoading()` 并清空全部流式游标，保证每轮开独立新气泡。回归：`tests/test_turn_start_reset_cur.js`。
- **空议题不可发起 / 续写**：辩论模式主按钮（开始讨论 / 继续讨论）在输入框为空时**禁用**，且后端 `start` 对空 `task` 直接广播 error 拦截——达成一致后若想继续必须输入新议题，空点「继续讨论」不会让 agent 空跑一轮。（前端 `input` 事件实时刷新按钮可用态；`refreshSendBtn` 以 `#task` 是否有内容为准。）
- **Team 选择必须随发起/续跑落库（防静默降级成 2 agent）**：`handle_start` 每次发起都按 `msg["team_id"]` 把所选 Team 写回会话（`store.update_session_team`）；「新建会话」弹窗的 `#nTeam` 默认预填 composer 当前 `#selTeam` 值。否则 stored team_id 停留在创建默认 `teams[0]`，重开会话会被静默降级（实测五子棋会话：首跑 3g 但 stored=2g，续跑无裁判）。回归：`tests/test_team_persist.py`（后端持久化）、`tests/test_new_session_prefill.js`（弹窗预填）。
- 共识产物沉淀到项目目录 `<项目>/.agentchat/sessions.json`（每条会话含 `messages` / `agent_sessions` / `conclusion`）；以**会话 + 各 agent 持续 CLI 会话**隔离，不跨会话串。记忆的"真相源"是 agent 各自的 CLI 会话（见 FR6），本地仅存结论展示用。

### FR4 控制能力
- 开始 / 停止（立即终止）/ 暂停 / 继续（仅辩论模式）。
- 人工介入（inject）：插入一条人类消息作为下一轮特殊输入，agent 基于它继续（非停止）。
- **控制指令必须有反馈**：没有运行中的会话，或在对话模式下点这些按钮，后端返回明确的 error 事件说明为什么无效；不允许「点了毫无反应」。

### FR4.1 「中止」与「继续」（turn 级中断，2026-09-14 已实现）
> 需求来源：用户实测「让 codex 继续下棋，结果一直思考中，最后失败报错」「很多对话工具都能中止输出，因为有时模型会死循环」。既有「暂停/停止」**只在轮边界生效**（当前发言必须跑完才停），对死循环无能为力 → 新增一套 turn 级能力。

- **与既有控制互不干扰**（用户明确要求「做成一个单独的功能」）：三层语义各自独立，不合并按钮、不共用状态：

| 能力 | 作用层级 | 生效时机 | 适用模式 |
|---|---|---|---|
| 暂停 / 恢复 / 停止 | 轮边界 | 当前发言跑完后，在下一位开始前 | 仅辩论模式 |
| **中止** | **在途 turn** | **当场掐断正在生成的输出** | **两种模式都可用** |
| **继续（重说）** | **turn 级** | **由被中止的 agent 重新完整发言** | **两种模式都可用** |
| 底部「继续讨论」 | 新一轮 run | 需输入新议题，发言顺序自第一个 agent 重新开始 | 按模式 |

- **中止必须在对话模式可用**：单 agent 对话最容易被死循环卡住，故不受「辩论模式专属」限制（对比：pause/resume/stop 在对话模式仍明确拒绝并给出原因）。
- **作废口径（用户确认）**：被中止的发言**仍然落盘并显示**（灰化气泡 + 「已中止」角标），让用户能看出「中间出过错」；但**不计入轮次、不作为其他 agent 的上下文、不作为结论来源**。
- **续接口径（用户确认）**：点「继续」由**被中止的那个 agent**、从**被中止的那一轮**重新发言——既不重置回第一个 agent，也不消耗半轮；轮次预算接着算。续接时向该 agent 注入「上次发言已被中止、请重新完整发言」提示（其 CLI 会话里仍留着那半截，不提示会顺着半句续写）。
- **交互形态（用户确认）**：复用主按钮槽位，不新增常驻按钮——空闲=「发送/开始讨论/继续讨论」、生成中=「中止」、有未兑现的续接=「继续（<agent> 重新发言）」；原辩论模式 ctrl 行的「继续」改名为「恢复」（它只是解除暂停，避免与新的「继续」混淆）。
- **中断通道（协议优先、硬停兜底）**：codex app-server → `turn/interrupt{threadId,turnId}`（实测毫秒级生效且长连接可复用）；claude → stdin 写 `control_request{subtype:interrupt}`（实测中断后 0.01s 收尾、`--resume` 仍可续接）；codex exec 兜底路径 → 整组 SIGTERM/SIGKILL。协议帧发出后 2.5s 内若仍未收尾，看门狗整组硬停（防个别后端不响应中断）。

### FR5 终止条件（三种并存 + 首轮议题判定）
1. **上限自动停**：`max_rounds`（发起讨论时配置，整场统一上限）**=「每个 agent 发言次数」**（N 轮即每个 agent 发 N 次 = 共 N×agent 数次发言），跑满即停。
2. **手动停止**：前端「停止」按钮 → 立即终止。
3. **自发收敛（精确条件 + 最小轮数保护 + 两阶段确认）**：agent 认为讨论已达共识时**主动发起终止**并停止讨论；终止须满足：
   - **最小轮数保护**：至少完成两轮完整往返（每个 agent 都发过两次言，即 `round_i >= 2*N-1`，`N`=agent 数）后才允许终止，杜绝「第二个 agent 一轮就草草终止」。
   - **共识确认真（两阶段）**：单 agent 调用终止不构成结束，须另一方也确认（见 FR5.3a）。
   - **当前实现（end_discussion 工具调用，2026-08-18 已实现）**：agent 通过调用结构化工具 `end_discussion(reason)` 表达终止意图，工具 handler 内做最小轮数 gate（不达标返回 `is_error` 失败、agent 自行放弃）与两阶段确认（提议 + 对方确认才终止）——比纯字符串可靠：gate 是结构性的、非词法匹配（见 FR5.3a）。
   - **旧机制降级为兜底**：独立一行 `TERMINATE` 关键词检测仍保留（未达最小轮数一律当普通文本继续），提示词已不再引导 agent 输出它。
   （注：`inject` 是「继续」不是「停止」；聊天文字不会被当作指令解析。）
4. **共识终止提示词（每轮下发）**：辩论模式每轮提示词都含「共识终止」条件——**强制终止只能通过调用 `end_discussion(reason)` 工具表达**（reason 填一两句共识结论），**禁止用普通文字表达终止意图**（如「我同意结束」不会被当作终止信号，避免 R1 等弱工具调用模型只输出文本不调用工具）；并明确「至少两轮完整往返才会考虑结束」「调用后还需对方确认」；**达到最少轮数后每轮追加硬提醒**：无提议时提醒「已到第 N 轮，若认为已达一致请调用 end_discussion 收尾」、对方已提议时推送「对方已提议终止（理由），认同请调用确认」、自己已提议时提示「等待对方确认」——弥补 gemma/r1 等弱工具调用模型在长辩论中不主动调用的问题。已**移除**原先「首轮判定议题不可讨论即终止」的诱导指令（它会导致第二个 agent 一轮就腰斩整场、首轮 agent 没机会再发言）。最小轮数保护由工具 handler 结构性保证（FR5.3a），提示词仅做引导。
   - **token 友好喂词**：每轮只把「上一轮对手的发言」回传给本方，并锚定「最初议题」，不再每轮搬运整段双方对话 / 累积记忆摘要（记忆仅作前端展示，不注入 prompt）。续开新议题时，把「最初议题 + 上轮结论」回传给首 agent，并让其**基于上轮结论与本轮新议题判断能否开启新讨论**；收敛时把结论格式化存盘，下一轮新议题直接复用，避免重新搬运历史。

### FR5.3a 终止工具 `end_discussion(reason)`（已实现，2026-08-18）
把「中止讨论」做成注册进每个 agent 的一个**受护栏工具（guarded tool）**：工具始终可被调用，但能否真中止由 gate 判定（`round_i < 2*N-1` 时返回 `is_error` 失败），agent 靠工具结果自适应回路自行放弃调用。比纯字符串/哨兵可靠（gate 是结构性的，非词法匹配）。
- **注册方式（2026-08-19 终版：stdio MCP + 网关双向改名 + prompt 双路径）**：`end_discussion` 由项目级 `.mcp.json` 注册的 **stdio MCP server**（`backend/terminate_signal_mcp.py`）提供真工具实现。关键修复（多轮实测定位）：① claude-code 2.1.212 的 stdio MCP 用 **JSONL**（每行一个 JSON）传输，`_read_frame` 已兼容 JSONL + Content-Length 双格式；② executor 改用 `--output-format stream-json --input-format stream-json --verbose`（SDK 同款，`-p` 旧模式 MCP 加载不可靠），prompt 经 stdin user 帧传入，`--session-id/--resume` 会话机制不变；③ gemma 对 `mcp__` 长前缀工具名不稳定，网关**双向改名**——转发 tools 时去前缀（模型见干净名 `end_discussion`）、翻译 tool_calls 回 claude 时还原前缀（claude 匹配 MCP server 执行）。链路实测：stream-json + `.mcp.json` → gemma native 调用 → MCP 返回「已收到你的中止提议」**成功（无 No such tool available）**。不支持工具调用的模型（`deepseek-r1:14b`，R1 不支持 function calling，Ollama 实测 tools=Y 仍 NONE）自然回落到 **prompt 文本 json 兜底**（编排层 `_extract_text_tool_call` 解析）——两条路径并存。**支持工具调用的模型也可能偶发走文本路径**（gemma4:26b 实测：116 份 transcript 中 6 份含真 `tool_use`、工具日志 `proposed 3 / confirmed 7`，另有少量轮次把调用写进了正文），故兜底解析是长期保留的第二条通道，不是「不支持工具的模型专用」。
- **gate 与状态（编排层权威；MCP 服务为无状态确认通道）**：多会话并行后共享状态文件会串场，故判定全部落在编排层内存状态机（MCP 服务 `tools/call` 一律返回成功确认文本，仅提供工具调用通道让模型发结构化 `tool_use`）：
  1. `round_i < 2*N-1` → 编排层拒绝（工具日志记 `rejected`），不记录提议状态；agent 继续产出内容。
  2. 达标且无提议 → 编排层记提议方+理由（日志 `proposed`）；提示词已说明「调用后需对方确认，可能继续讨论」。
  3. 对方也调用（`proposed_by ≠ current_agent`）→ **确认达成，终止**（日志 `confirmed`）；`reason` 作共识结论存盘（确认方未给 reason 用提议方的）。
  4. **每次调用均落工具日志** `tools/<sid>.jsonl`（rejected/proposed/repeat/confirmed + agent/round/reason/ts），前端「工具」按钮可查。
- **确认无时间窗限制**：只要讨论未被终止，之后任意一轮对方再调即算确认（不要求「下一轮立刻确认」）。
- **最小轮数定义**：「2 轮」= 双方各发言 1 次 = 1 轮（`round_i >= 2*N-1` 等价于双方各发 2 次），与 FR5.3 的 floor 一致。
- 失败用 `is_error=true` 返回，模型当作真实错误自我纠正；被拒后该轮仍能产出实质内容。fake agent 的 `fake_terminate_round` 已改为发结构化 `tool_use(end_discussion)`（不再输出 TERMINATE 文本）。
- **codex 侧接入（2026-09-11 补齐）**：复用**同一个** MCP 脚本（`backend/terminate_signal_mcp.py`，纯 stdlib），但注册方式不同——claude 走项目级 `.mcp.json`，codex 无该项目级机制，改用 `-c key=value` 逐次注入配置覆盖（点号路径，**不动用户 `~/.codex/config.toml`**）：
  - `-c mcp_servers.terminate-signal.command='<python>'` + `.args=['<root>/backend/terminate_signal_mcp.py']`（TOML 字面字符串，路径免转义）；
  - `-c mcp_servers.terminate-signal.default_tools_approval_mode="approve"` —— **必需**：codex 的 MCP 工具默认走审批，而 `codex exec` 非交互、无审批人 → 自动返回 `user cancelled MCP tool call`，工具永远调不通（实测默认值与 `auto` 均被取消，只有 `approve` 能真正执行；合法值 `auto/prompt/writes/approve` 由 codex 对非法值的报错枚举得出）。
  - **事件映射**：codex 的 MCP 工具调用 item 含 `server`/`tool`/`arguments`/`result`/`error`/`status`，executor 把它映射成与 claude 侧**完全一致**的 `("tool_use", {"name": "end_discussion", "input": {"reason": ...}})`，编排层终止状态机才能收到 codex 的票（否则表现为「codex 只会说话、不会投终止票」）。只认 `item/completed`（会发 `started`+`completed` 两条，取 completed 保证必有且不重复）；MCP 回执文本嵌在 `result.content` 内，不得被当发言文本渲染进气泡。
    - ⚠️ **item.type 命名随通路而异（2026-09-15 修复）**：**app-server（本 app 默认路径）发 `mcpToolCall`（驼峰），exec（`codex exec --json`）与 rollout 回放发 `mcp_tool_call`（下划线）**。原实现只判下划线 ⇒ app-server 下 codex 的票**实时全丢**（实测 s_f85043cf：两轮真调用、rollout 内 `mcp_tool_call_end` 均 `Ok`，状态机一票未见，阈值 2 永不满足，辩论只能靠轮次耗尽收尾）。现已由单一谓词 `_is_mcp_tool_item`（`_MCP_TOOL_ITEM_TYPES = ("mcpToolCall","mcp_tool_call")`）统一判定，app-server 通知与 exec 解析共用。
    - 掩盖点：**落盘消息里能看到 codex 的工具块**，是**事后对账**读 rollout（下划线那条）补上的——实时与回放两条路的差异把 bug 藏住了。

### FR5.3b 多 agent 扩展（≥3 agent 的终止规则与发言回传；**已实现**，2026-08-21 落地）
> 与 FR5.3a 同属「多 agent 正确性」需求，一次性实现。目标：2 agent 行为不变（向后兼容），3+ agent 时讨论对所有参与者信息对称、终止需多数同意而非少数人拍板。
>
> 背景缺口（实测/代码确认）：
> - **终止规则过弱（已实现修复）**：旧状态机「提议方 + 任意 1 个不同 agent 确认即终止」（`proposed_by ≠ current_agent` → confirmed）。2 agent 下这恰等于全员同意；**3+ agent 下退化为「2 票拍板」**——A 提议后 B 随手调用 end_discussion 就终止，C/D/E 完全无发言权。2026-08-21 已改为子项1 的多数同意集合（见下）。
> - **发言回传信息断链（已实现修复）**：旧实现每轮只回传「上一个 agent 的发言」（`_build_prompt` 从 history 倒序取第一条非自己/system/human）。2 agent 下交替发言恰好等价于「看到对方全部发言」；**3+ agent 轮转时每个 agent 只能看到紧邻前一个 agent 的发言**，其他 agent 的发言从未进入其 prompt，讨论退化为「两人小圈对话」。2026-08-21 已改为子项2 的全量回传（见下）。

**子项 1：终止改为「多数同意」**
- 语义：终止需**严格多数**的 agent 显式同意——同意阈值 = `⌊N/2⌋ + 1`（N=agent 数，向下取整+1；N=2 → 2，与现有两阶段确认完全一致；N=10 → 6）。
- 状态机改造：`terminate_proposed_by`（单提议方）→ 记录**同意集合**（每个 agent 一次 `end_discussion` 调用即计一票；同方重复调用仍只算一票）；当同意集合大小 ≥ 阈值时收敛终止，`reason` 取最后同意方（或提议方）的结论。
- 保留：最小轮数 gate（`round_i >= 2*N-1`）、`rejected/proposed/repeat/confirmed` 工具日志、无时间窗限制（任一后续轮次达到多数即终止）。
- 不做「全部同意」（unanimous）：10 个 agent 有 1 个不同意会拖到 `max_rounds` 跑满，条件过强（用户明确否决）。

**子项 2：发言回传改为「本方上次发言后的全部他人增量」**
- 语义：每轮 prompt 回传「**本方上一次发言之后、本次发言之前，所有其他 agent 的发言**」（按发生顺序），保证每个 agent 都看得到全体其他参与者的观点，而不是只看紧邻上一个。
- 实现要点：`_build_prompt` 的 `last` 单条查找改为「定位本方上次发言的下标 → 取其后所有非 self/system/human 的发言」；首轮无他人发言不回传；2 agent 时结果与现状等价（对方上一句 = 全部增量），无需特判。
- token 考量：N 大或轮次深时增量可能变长，允许「按需截取最近 K 条」（K 可配置，默认不截），但必须保证「每个 agent 至少见过其他所有 agent 各一次发言」，不得退回只回传紧邻上一个。
- **任务背景补齐（2026-08-21 落地）**：任务只在 round0 经 inject 传给第一个 agent，其余 agent 首轮若只看到 delta 可能无法推断议题（象棋实测 d2 把 CLI 系统提示的技能列表误当议题走偏）。故每个 agent「就当前议题首次发言」时补注入任务背景（判定：history 中该 agent 最近发言早于最后一条 human「任务」消息即视为首轮）；非首轮不再重复搬运。
- 与 #16 单源时间线不变式一致：仅作为 delta 喂入端，仍不反向读取 agent CLI 会话拼装历史。

  - 辩论模式保留任务框、最大轮次、暂停/继续/停止、人工介入；
  - 运行期间主按钮禁用并显示「回复中…」/「讨论进行中…」，收到 `run_end` 后恢复。

### FR9 状态式 agent 会话（app↔agent 1:1 持续会话）
- **1:1 绑定、持续续接**：每个 agent 在某一 app 会话内各自持有**一个** CLI 会话（claude-code / codex），同一 app 会话里无论多少轮、多少议题都复用同一个；编排器每轮只把「对手上一句 + 本轮任务」作为新 user 消息续接，**绝不重新搬运整段历史**。
- **开新 app 会话才新建 agent 会话**：只有创建新会话时生成新的 CLI 会话 id；在已存在（含已中止）的同一会话里续开新议题，复用同一 agent CLI 会话，首轮仍下发「议题可讨论性」判定（见 FR5.4）。
- **点历史会话恢复对应 agent 会话**：CLI 会话 id 持久化在 `sessions.json` 的 `agent_sessions: {agent_name: cli_session_id}`；重开历史会话时经 `--resume <id>` 恢复，agent 保留其全部历史上下文。
- **续接机制（已对真实二进制核实）**：
  - **claude-code**：**首次**用 `--session-id <uuid>` 注册会话，后续续接（含历史会话恢复、同会话后续轮）改用 `--resume <id>`——claude 2.x 不允许复用 `--session-id`（同 id 第二次启动即报 `Session ID ... is already in use`），故续接必须走 `--resume`。若续接时仍遇 `already in use` 或 `session not found`（异常退出残留锁 / 历史恢复读到坏 id），executor 自动换新 id 重试一次（自愈）。
  - **codex（app-server 持久进程）**：每个 `AgentRuntime` 拉起**一条 app-server 长连接**跨本会话多轮复用（`initialize` → `thread/start` 得 `thread.id` → 多次 `turn/start`）；同一 thread 在进程内持续，跨轮记忆天然保留，**无需每轮 resume**。CLI 会话 id = `thread.id`，持久化进 `sessions.json` 的 `agent_sessions` 与 `cli_session_id`（历史恢复复用）。**`thread/resume` 跨进程恢复实测可用**（2026-09-14 订正，见下条「回收必须整组 + 先 SIGTERM」）：新进程 resume 旧 thread 后提问「刚让你记的数字」，模型正确答出 `777`，说明跨进程记忆保留。故历史重开/消息续接走 resume，失败（无 rollout / 超时）才回落 `thread/start` 新建。握手失败（进程起不来 / `initialize` 无响应 / `thread/start` 失败）→ 抛 `_CodexAppServerUnavailable`，run() 据此回退 `codex exec`（兜底，等价旧行为）。
  - **回收必须整组 + 先 SIGTERM（2026-09-14 修复，订正前一版结论）**：`codex` 是**两层进程**——`node /usr/local/bin/codex`（壳）再 spawn 真正的原生 app-server。原先只 `proc.kill()` 壳，原生子进程被 init 收养（PPID=1）**继续存活并持有 thread 与 stdio 管道** → ① 进程泄漏（实测一次会话留 1 壳+1 原生+1 MCP 子进程）；② 壳被 SIGKILL 时 codex 来不及落盘 rollout，下一条消息 resume 报 `no rollout found` → 静默新建 thread、**丢失模型 in-context 记忆**（此前「resume 跨进程静默 EOF」的结论即由此污染，不成立）。现改为：spawn 一律 `start_new_session=True`（自成进程组）＋ `_kill_proc_group()` 先 `killpg(SIGTERM)`（给 codex 机会落盘 rollout）超时再 `SIGKILL`，并校验 `pgid != 自身 pgid` 防误杀本服务。真机验证：闭环时 3 进程全清、0 残留；跨进程 resume 记忆命中。
  - **断流可诊断（2026-09-14）**：app-server 的 stderr 原先**全部丢弃**，导致线上「连接断开」只有一句无信息量的错误。现保留尾部 24 行 + 退出码，EOF 时随错误一并上报（如 `codex app-server 连接断开（退出码 1；stderr 尾部: …）`）。
  - **审批类 ServerRequest 自动批准**：app-server 把执行命令/打补丁/权限/MCP 询问/动态工具作为反向 ServerRequest 发来，读循环就地自动应答（exec→`decision:"accept"`、applyPatch→`decision:"approved"`、elicitation→`action:"accept"`、requestUserInput→`answers:{}`、permissions→回授 `scope:"session"`、动态 tool→`success:true,contentItems:[]`），否则 codex 阻塞等应答、回合卡死。

### FR10 Agent 级「本地模型网关」接入（走 Claude Code 外壳加载本地模型）
- **目标**：让某个 agent 通过 Claude Code 外壳加载本地部署模型（如 Ollama 的 gemma / deepseek），而**不修改 Claude Code 自身任何配置**，且**绝不串到默认后端**（如全局配置的 deepseek）。
- **机制（per-agent 隔离配置目录，非仅 env 注入）**：`AgentConfig` 增加可选字段 `base_url`（网关地址，如 `http://127.0.0.1:8777`）与 `api_key`（网关 key，可空）。当 agent 配置了 `base_url`，executor 为该 agent 生成**隔离配置目录**（`~/.cache/agentchat/claude-cfg/<agent_name>/`，按 agent 名固定、幂等），写入一份复制自用户 `~/.claude/settings.json` 的 `settings.json`：去掉 `enabledPlugins`（避免临时目录缺失插件文件报错），并把 `env.ANTHROPIC_BASE_URL` 改写为该网关、`ANTHROPIC_API_KEY` 补 dummy（网关放行任意值）、`ANTHROPIC_CUSTOM_MODEL_OPTION` 设为 `<model>`；再用 `CLAUDE_CONFIG_DIR` 指向它拉起 claude 子进程。
  - **为何不能只靠子进程 env 注入**：claude 2.x 会把 `~/.claude/settings.json` 的 `env` 字段合并进运行时并**覆盖同名进程环境变量**，仅靠 `os.environ` 副本覆盖 `ANTHROPIC_BASE_URL` 会被全局配置（如指向 deepseek）盖掉、per-agent 网关失效。隔离配置目录让子进程只读这份改写后的配置，**完全不动用户全局 `~/.claude`**，满足「不改 Claude Code 配置、不串默认后端」。
  - 认证沿用用户 settings 中的 `ANTHROPIC_AUTH_TOKEN`，网关侧放行任意 key；隔离目录内的 session 历史与 `--resume` 续接机制一致（按 agent 名固定路径，跨进程可 resume）。
- **内置翻译网关（开箱即用，无需另起 litellm、不改 Ollama 配置）**：本系统自带一个 Anthropic↔Ollama 翻译网关（`backend/gateway.py`，路由 `POST /v1/messages`）。它把 Claude Code 的 Anthropic Messages 请求翻译成 Ollama 的**原生 `/api/chat` 请求**（含 system / messages / tool_use / tool_result 的双向转换，流式 SSE 与非流式均支持），转发到 Ollama 原生端点（默认 `http://localhost:11434`，由全局设置 `ollama_base_url` 或环境变量 `OLLAMA_BASE_URL` 配置）。**只读取 Ollama 既有端点，完全不改动 Ollama 自身配置**。典型链路：`claude → ANTHROPIC_BASE_URL=本后端(:8777) → 内置网关 → ollama/gemma(:11434)`。
  - **上下文长度由本网关自控（不动 Ollama 全局）**：网关走原生 `/api/chat` 而非 OpenAI 兼容端点，唯一原因是只有原生端点接受 `options.num_ctx`——实测 OpenAI 兼容端点忽略 `num_ctx`/`options.num_ctx`，会把上下文拉满模型原生 128k（deepseek-r1:14b 单份吃掉 ~34GB 显存），而 Ollama GUI 聊天默认 context 小（同模型仅 ~10GB）。网关向 Ollama 传 `options.num_ctx = settings.ollama_num_ctx`（默认 **16384**，全局设置可改、即时生效），对辩论场景足够，且把单份显存压到 ~12GB；多个同模型 agent 共享同一份加载（不叠加）。历史 messages 里的 `tool_calls` 在转发前自动转为 Ollama 原生格式（arguments 由 JSON 字符串解析为对象），否则 Ollama 直接 400 拒绝整轮。
- **预置「Claude Code (Gemma)」agent**：`data/config.json` 已内置 `ag_gemma`（claude-code 类型，`base_url=http://127.0.0.1:8777`、`model=gemma4:26b`，`gemma4:26b` 须换成你本机实际 `ollama pull` 的 gemma tag），左栏可直接看到它、放进任意 team 即可用——前提是本机 Ollama 已 `ollama pull` 对应 gemma 模型（如 `gemma4:26b`）。这就是「选了直接能用」。
- **agent 表单「模型来源」选择**：编辑 claude-code agent 时，表单提供三种模型来源——**默认**（直接显示当前生效默认模型名，无需配置）、**本地 Ollama · gemma**（选了自动填好 `base_url=http://127.0.0.1:8777` 与 `model=gemma4:26b`，注意把模型名改成你本机实际 pull 的 gemma tag）、**自定义网关**（指向 litellm 等其它翻译网关）。默认来源隐藏网关字段，仅显示当前生效模型；切换来源实时联动。
- **配置可改**：在 agent 表单填写/修改 `base_url` / `model` / `api_key` 即切换接入的本地模型，持久化进 `data/config.json` 的 `agents[]`，无需改代码。
- **左栏直接显示所连模型**：agent 节点在类型徽章后追加一个模型标签（名称不被模型绑定）：配了 `base_url` 显示具体本地模型（紫色 `model-local`，hover 显示网关地址）；显式指定 `model` 显示该云端模型（蓝色 `model-cloud`）；二者都未配时，**claude-code 类型显示全局默认模型名**（灰色 `model-default`，默认模型名由全局设置 `default_model` 提供——留空则后端自动探测 Claude Code 当前默认，即 `claude` 启动画面显示的模型，如 `claude-sonnet-4-…`；其它类型无探测仍显示「默认」）。由此两个连不同大模型的 claude-code agent（如一个 `ollama/gemma`、一个默认 deepseek）在列表里一眼可辨。
- **默认模型名也要真实显示（不是「默认」占位）**：用户要求即使走默认配置，列表与配置里也要显示模型真实名字（类比 `claude` / `codex` CLI 启动画面）。后端 `store.detect_claude_default_model()` 按 `ANTHROPIC_DEFAULT_MODEL` > `~/.claude/settings.json` 的 `model` > `~/.claude.json` 的 `model` 探测 Claude Code 当前默认；`store.detect_codex_default_model()` 按 `CODEX_MODEL`/`OPENAI_MODEL`/`OPENAI_API_MODEL` > `~/.codex/config.toml` 的 `model` 探测 Codex 当前默认（如 deepseek-v4-flash）。全局设置 `default_model` / `default_model_codex` 可分别 pin 二者（优先级最高）。agent 配置表单内「当前生效模型」随模型/网关输入实时联动，全局设置提供「Claude Code 默认模型」「Codex 默认模型」两项。

### FR11 思考模型（thinking）的「思考过程」展示与逐字流式- **目标**：接入思考模型（如 Ollama 的 gemma 等会输出推理链 `reasoning` 的本地模型）时，前端能像主流 AI 工具一样**折叠展示模型的思考过程**，且**答案逐字吐出（打字机效果）**，而非整段一次性出现。
- **机制修正（claude-code 不丢弃标准 thinking 块）**：2026-08-18 真机复核——claude-code（2.1.212）对本地模型经网关返回的响应，**会原样存储标准 `thinking` content block（带 `signature`）进 transcript**，且 `claude --resume` 能正确读取、回传该 thinking 块续聊（不报错、思考不被当正文）。原「外壳会吞掉 thinking 块、只能塞裸 text + 哨兵」的论断不成立（当时可能误测了 `<thinking>` 标签或旧版本行为），故改为原生协议。
- **机制（原生 thinking 块 + text 块）**：内置网关 `backend/gateway.py` 把 Ollama 的 `reasoning`/`reasoning_content` 翻译为**原生 `thinking` content block（index 0，带占位 `signature`）**、`content` 翻译为**`text` content block（index 1）**转发（流式：`thinking_delta` → `signature_delta` → 收口 → `text_delta`）。claude-code 原样落盘，**原生 `claude --resume` 与外部 UI 工具均可直接识别「思考 / 答案」**，transcript 不再残留哨兵。executor `_parse_claude_transcript` / `_parse_claude_line` 同时兼容原生 `thinking` 块与旧版哨兵 text 块（哨兵仅作读取旧 transcript 的兜底清洗，`_clean_sentinels`）。orchestrator 把 thinking 作为独立 `thinking` 事件实时广播并落盘进 `messages[].thinking`（刷新后历史仍可见、渲染为可折叠块）；thinking 不回灌 prompt 上下文。answer 作为 `token` 事件；前端把 thinking 渲染为可折叠的 `💭 {agent 名} 的思考过程` 气泡（按 agent 类型着色：claude-code 蓝 / codex 绿 / fake 橙，与正文气泡配色一致）、answer 经 `_replay` 回放为逐字流。
- **非思考模型兼容**：模型未产出 `reasoning` 时，网关只发单个 answer 文本块（不加哨兵），executor 默认按答案处理，行为与以往一致。
- **codex 侧的思考来源（2026-09-11 补齐）**：codex **不在 `exec --json` 事件流里上报 reasoning**（实测只有 `thread.started` / `turn.started` / `item.completed` / `turn.completed`，推理仅以 `usage.reasoning_output_tokens` 计数出现；`hide_agent_reasoning=false` + `show_raw_agent_reasoning=true` 也不会输出）。但它的 rollout 文件（`~/.codex/sessions/…/rollout-*.jsonl`）里有**明文**：`response_item` → payload.type=`reasoning` → `content[].text`（type=`reasoning_text`）。故 `_run_codex` 在吐「正文 / 工具调用」之前，先把 rollout 里**新增**的 reasoning 作为 `thinking` 事件吐出 —— codex 的正文是**整块**在回合末（`item.completed`）到达、reasoning 早已落盘，因此顺序天然对齐原生（思考在前、正文在后），不需要另造顺序逻辑；对账时 `_parse_codex_transcript` 同样按原生顺序产出 thinking/text/tool_use 块。
- **claude 侧改真流式（2026-09-11）**：claude `--output-format stream-json` **默认只发整块 assistant 消息、不发 delta**（实测一轮：38 system / 2 assistant / 1 result，零 delta）——此前界面上的"逐字效果"其实是 `_replay` 把整块文本演出来的。加 `--include-partial-messages` 后才发 `stream_event` → `content_block_delta`（实测 72 text_delta + 53 thinking_delta），**正文与思考都是真增量**。两处配套改动：① `_parse_claude_line` 解包 `stream_event`（delta 包在 `{"type":"stream_event","event":{…}}` 里）；② **去重**——开 partial 后同一段内容会既以 delta 到达、又出现在最终整块 assistant 消息里（不去重界面显示两遍），故以 `runtime._streamed_text/_streamed_think` 记账、在 `message_start` 复位，解析整块时跳过已流式吐过的正文/思考，但 **tool_use 仍从整块消息取出**（delta 只有半截 JSON）。旧版本 claude 无此 flag 时 `_run_claude` 自愈降级（关掉 flag 重试）。实测端到端：69 条 text 事件（最长 3 字符）+ 152 条 thinking 事件，合计 100 字、无重复。回归测试 `tests/test_claude_stream.py`。

### FR12 codex 真流式（app-server JSON-RPC over stdio，2026-09-14 已实现）
- **目标**：codex 走 `codex exec --json` 时**正文是整块**在回合末（`item.completed`）到达、无流式增量（见 FR11 的 codex 思考来源条），界面只能"整段冒出"；且 exec 会话 `source=exec`、ChatGPT 桌面端不列。`codex app-server` 通过 JSON-RPC over stdio 提供 `item/agentMessage/delta`（正文真增量）+ `item/reasoning/textDelta`（思考真增量）+ `turn/interrupt`（真中断）+ 会话 `source=vscode`（桌面端可见），故把 codex 主路径换成 app-server，旧 `codex exec` 保留为**自动兜底**。
- **协议（已对真实二进制 codex-cli 0.146.1 核实）**：`initialize`（`clientInfo`）→ `thread/start`（返回 `result.thread.id`，即持久化续接的 CLI 会话 id）→ `turn/start`（required `input:[{type:"text",text}]` + `threadId`）。真增量事件：`item/agentMessage/delta`（text）、`item/reasoning/textDelta` / `item/reasoning/summaryTextDelta`（thinking）；回合结束 `turn/completed`（status=completed）；`end_discussion` 经 `item/tool/call`（`tool` 含 `end_discussion`）或 `item/completed`（`type=mcp_tool_call`）捕获为 `tool_use`。
- **持久进程 + 跨轮复用**：每个 `AgentRuntime` 拉起一条 `codex app-server` 长连接，跨本会话多轮复用同一进程/同一 thread——跨轮记忆天然保留，**无需每轮 resume**。会话结束（`orchestrator.Session.start()` 的 `finally`）调 `rt.aclose()` → `_kill_appserver()` 回收进程（**整组**杀壳+原生 + 取读循环 task），避免长连接泄漏。
- **回退策略**：`_ensure_appserver` 握手（进程拉起 / `initialize` / `thread/start`）任一失败抛 `_CodexAppServerUnavailable`，`run()` 的 codex 分支 `except` 后自动 `async for` 旧 `_run_codex`（`codex exec` 兜底，等价旧行为）。握手成功后的单轮错误按 `("error", …)` 产出、**不回退**（避免一轮失败就整个降级）。`thread/resume` 跨进程恢复**实测可用**（2026-09-14 订正）；历史重开/消息续接仍带超时尝试、失败（无 rollout / 超时）回落 `thread/start` 新建。
- **审批类 ServerRequest 自动批准**：app-server 把命令执行/打补丁/权限/MCP 询问/动态工具作为反向 ServerRequest 发来，读循环 `_as_autoanswer` 就地自动应答（exec→`decision:"accept"`、applyPatch→`decision:"approved"`、elicitation→`action:"accept"`、requestUserInput→`answers:{}`、permissions→回授 `scope:"session"`、动态 tool→`success:true,contentItems:[]`），否则 codex 阻塞等应答、回合卡死。
- **模型/参数注入**：app-server **不接受 `-m`**（实测 "unexpected argument '-m'" 直接退出）→ 模型经 `-c model='<model>'` 覆盖，并在 `thread/start` 的 `model` 参数再确认；**不接受 `--skip-git-repo-check`**（实测 rejected），但 `thread/start` 在非 git/未受信目录实测可直接成功，故不再带该 flag。原有 `-c mcp_servers.terminate-signal.*` 注入原样沿用。
- **reasoning 兜底**：若本轮模型未发 reasoning delta（如 deepseek 高 effort 不吐 thinking delta），回合末从 rollout 文件补本轮新增 reasoning（仅补 `_as_reasoning_seen` 之后增量，避免跨轮重复）作为 `thinking` 事件；与 FR11 的 codex 思考来源逻辑一致。
- **回收必须整组 + 先 SIGTERM（2026-09-14 修复，含对前一版结论的订正）**：`codex` 是**两层进程**——`node /usr/local/bin/codex`（壳）再 spawn 真正的原生 app-server。原实现只 `proc.kill()` 壳 → 原生子进程被 init 收养（PPID=1）**继续存活并持有 thread 与 stdio 管道**：① 进程泄漏（一次会话实测留 1 壳 + 1 原生 + 1 MCP 子进程）；② 壳被 SIGKILL 时 codex 来不及落盘 rollout，下一条消息 resume 报 `no rollout found` → 静默新建 thread、**丢失模型 in-context 记忆**（前一版文档「resume 跨进程静默 EOF」的结论即被此污染，**不成立**）。现改为：spawn 一律 `start_new_session=True`（自成进程组）+ `_kill_proc_group()` 先 `killpg(SIGTERM)`（给 codex 落盘 rollout 的机会）超时再 `SIGKILL`，并校验 `pgid != 自身 pgid` 防误杀本服务；`codex exec`/`claude` 的 `_stream_subprocess` 同样整组回收（超时/异常路径）。真机验证：闭环 3 进程全清、0 残留；新进程 resume 旧 thread 后仍能答出先前记下的数字（跨进程记忆保留）。回归：`tests/test_codex_appserver.py::TestKillProcGroup`（真实进程整组杀 / 已退出不杀 / 拿不到 pgid 退单体 / **绝不杀自身进程组**）。

### FR13 codex agent 的模型服务来源（本地 Ollama 直连 / 自定义网关，2026-09-16 已实现）
- **目标**：codex 类型的 agent 也能像 claude-code 那样在表单里选「模型来源」，把某个 codex agent 指到**本机免费 Ollama**（gemma 等），**不修改 `~/.codex/config.toml`**，也**绝不因为「默认」而落到远程付费模型**（本机 `~/.codex/config.toml` 的 `model_provider=deepseek` + `model=deepseek-v4-flash` 指向 `api.deepseek.com`，是要花钱的远程 API）。
- **与 claude 侧的差异（为何不能复用内置网关）**：claude 走本 app 的内置翻译网关（Anthropic↔Ollama，`:8777`）；codex 说的是 OpenAI **Responses** 协议，本网关只翻译 Anthropic 协议，故 codex 必须**直连模型服务自身的 `/v1/responses`**。实测前提：codex-cli 0.146.1 **只支持 `wire_api="responses"`**（不再支持 `chat`），而本机 Ollama 0.33.3 **已实现 `/v1/responses`**（`GET` 返 405 而非 404），故 codex 可直连 Ollama 跑 gemma。
- **机制（一律命令行 `-c` 注入，等价于手工 `codex exec -c …`）**：agent 配了 `base_url` 即表示「本 agent 走指定模型服务」，`_codex_provider_overrides()` 据此产出 `-c`：
  - 指向本机 Ollama（地址含 `11434`）→ 用 codex **内置** provider `ollama`：`-c model_provider="ollama"`；
  - 其它地址 → 注册自定义 provider `agentchat`（`model_providers.agentchat.{name, base_url, wire_api="responses"}`，地址自动补 `/v1`）——内置 provider 名不可覆盖（实测 `model_providers.ollama.name` 报 reserved，故必须换名）；
  - 未配 `base_url` → 不注入，沿用 codex 全局配置（既有行为不变）。
  `codex exec` 与 `codex app-server` 两条命令构造共用同一实现。
- **配置可改**：agent 表单 codex 类型的「模型来源」＝ 默认 / 本地 Ollama · gemma（自动填 `http://localhost:11434` + `gemma4:26b`）/ 自定义网关（需 responses 协议）；保存即写入 `data/config.json` 的 `agents[]`。**修复**：原先 `submitAgent` 对非 claude 类型强制置空 `base_url`，codex 即便配了也会在下次保存时被抹掉。
- **副作用（第三方 CLI 固有行为，非 app 写入）**：codex 在某个目录跑过一次后会自己往 `~/.codex/config.toml` 追加 `[projects."<目录>"] trust_level = "trusted"`；app 自身**从不写**该文件（见开发文档 §5 机制 #41）。
- **验证**：`tests/test_codex_parse.py` 覆盖三例——「本机 Ollama → 内置 ollama provider」「非本机地址 → 自定义 agentchat provider」「未配 base_url → 不注入任何 provider」；另真机复测（2026-09-16，`agent-probes/probe_codex_paths.py`，本地免费 gemma）：**provider 选择与执行路径无关**——agent 配了本机 Ollama 后，默认分发仍走 app-server（探针实测未触发回退，`run()` 内 exec 调用次数为 0），产出的 rollout `source="vscode"`（桌面端可见）；`codex exec` 兜底路径的 rollout 为 `source="exec"`。

### FR14 codex 自带工具调用的捕获与显示（2026-09-16 已实现）
- **目标**：codex 调用**自带工具**（shell 执行、打补丁等，即非 MCP 的 `end_discussion`）时，气泡里能看到这次调用。此前**完全不显示**——不是前端画不出，而是后端从未捕获。
- **事实（2026-09-16 实测核对）**：codex **能**调用自带工具。放开沙箱后 `codex exec --json` 事件流为 `item.started`/`item.completed` + `item.type="command_execution"`、`command="/bin/bash -lc 'echo codex-tool-test'"`、`aggregated_output="codex-tool-test\n"`、`exit_code=0`；其 rollout 则是 `response_item.function_call`（`name="exec_command"`、`arguments='{"cmd": …}'`）后跟一条 `function_call_output`。
- **三条通路命名各异（同一份 codex）**：`codex exec --json` → `command_execution`（下划线）；app-server（本 app 主路径）→ `commandExecution`（驼峰）；rollout → `function_call` + `name=exec_command`。判定与提取收敛为**单一谓词 + 单张映射表**（`_CODEX_NATIVE_TOOLS` / `_codex_native_tool_use`），三条通路共用（与 FR5.3a 里 `mcpToolCall` / `mcp_tool_call` 的教训同源：别在分支里各写一份字符串判断）。
- **映射**：统一产出与 claude 侧同构的 `tool_use{name, input}`——命令执行 → `exec_command`（`input={command, [exit_code]}`）、文件改动 → `apply_patch`（`input={patch}`）。只认 `item.completed`（`started`/`completed` 成对上报，取 completed 既有保证又不重复计）。前端是**通用渲染**（不认工具名）⇒ **零改动**即可显示为「🔧 调用工具 exec_command」+ 参数折叠块。
- **对账同样认原生工具**：`_parse_codex_transcript`（rollout 对账）把非 `end_discussion` 的 `function_call` 也映射成 `tool_use`；否则打开历史会话时，「CLI 侧有工具块」会让 `store._merge_tool_blocks` 整体采信 CLI 版本，把实时落盘的原生工具块抹掉（表现为「刚看过的工具调用，重开一次就没了」）。工具回执 `function_call_output` **更新（2026-09-16，见 FR15）**：已映射为 `tool_result`——`is_error` 并非无据可依，可由回执头的 `Process exited with code N` 或 `exit_code` / `exitCode` 字段判定；同时**绝不**被当成正文混进气泡（已回归锁定）。
- **验证**：`tests/test_codex_parse.py`（exec 通路产 tool_use / `item.started` 不重复 / 谓词与命名 / rollout 对账保留原生工具 / 工具回执不进正文）+ `tests/test_codex_appserver.py::TestCodexNativeToolItems`（驼峰、下划线、`fileChange`、未识别类型忽略）；另用**真实 rollout**（2026-09-16 12:12 探针那次）零成本验证 `_parse_codex_transcript` 产出 `tool_use(exec_command)` 且时间线顺序为 `[tool_use, text]`（先调用后正文，与原生一致）。**端到端真机复测（2026-09-16，`agent-probes/e2e_codex_appserver_display.py`，本地免费 gemma）**：app-server 主路径跑通完整编排 → 前端事件流出现 `tool_use{exec_command, /bin/bash -lc 'echo app-server-e2e'}`、落盘消息 `blocks=[text, thinking, tool_use, text]` + `tool_calls=[exec_command]`（刷新后仍在），且模型报出的是**真实执行输出** `app-server-e2e`（非幻觉）；同一次复测用 `codex exec` 兜底路径亦捕获到同一工具（两条路径都能显示）。

### FR15 codex 工具「执行结果」的捕获与显示（2026-09-16 已实现）
- **目标**：codex 调用自带工具后，气泡里不只有「调用了什么」，还要能看到**执行结果**（输出 / 退出码），与 claude 侧一致。
- **事实（2026-09-16 实测核对）**：claude 侧本来就有——CLI 以 `user` 事件里的原生 `tool_result` 块上报，`_extract_tool_results` 解析后进气泡。codex 侧**三条通路都只产 `tool_use`、没有一处产 `tool_result`**：`_parse_codex_line`（exec 实时）与 app-server 的 `item/completed` 都只调 `_codex_native_tool_use`，`_parse_codex_transcript`（rollout 对账）连 `function_call_output` 分支都没有、`_normalize_turn` 也没传 `tool_results`。结果：所有 codex 会话的 `tool_results` 恒为 `[]`，界面「有命令、没输出」（用户实测发现，claude 侧正常）。
- **字段三通路各异，按候选兜底**：exec `--json` → `aggregated_output` + `exit_code`；app-server → 驼峰 `aggregatedOutput` + `exitCode`；rollout → `function_call_output.output`（字符串，回执头含 `Process exited with code N`）。故新增 `_CODEX_TOOL_OUTPUT_FIELDS` / `_codex_tool_output` / `_codex_native_tool_result` 三处共用：依次尝试候选字段（并兼容 `[{type:text,text}]` 列表），退出码优先取字段、否则从**剥离前全文**正则抠（退出码只在回执头里）；无输出且未失败则不产空块（避免界面出现空框）。
- **回执头剥离**：rollout 的 output 带执行元信息（`Chunk ID` / `Wall time` / `Process exited with code N` / `Original token count`），界面噪声 ⇒ 剥到 `Output:` 之后只留真正的命令输出，与用户预期「结果就是命令输出」一致。
- **位置与顺序**：rollout 侧按 `call_id` 把回执**插到对应 `tool_use` 之后**（并同步修正已记录的下标映射），缺 `call_id` 时顺序追加；exec / app-server 侧在同一条 `item.completed` 上先产 `tool_use` 再产 `tool_result`（时间线天然相邻）。
- **前端零改动**：编排层 `_run_turn` 早有 `kind == "tool_result"` 分支（拼块 + 广播 + 失败计 `tool_use_errors`），前端早有 `makeToolResultBlock`；失败结果按既有约定以失败样式渲染并计入 `exec_ok=false`。
- **历史会话可回填（用户问「现有会话里的结果能补吗」→ 能）**：修好解析器后，用既有工具 `python -m backend.reconcile_sessions <项目路径>` 重跑对账即可把 `function_call_output` 写回本地（`_merge_tool_info` 对非空 `tool_results` 本就以 CLI 为准覆盖）。2026-09-16 对 6 个项目回填出 **46 处 `tool_results` / 56 处 `blocks`**：codex3 五子棋裁判 c3 的 8 轮棋谱校验输出、两个agent 各会话的 `end_discussion` 回执、test5 侦探小说编辑轮的终止回执、agent-probes 的 4 条 `exec_command` 结果等；顺带补回 1 处历史遗留的 `tool_calls`（`list_agents`）。逐字段比对确认变更**只涉及工具类字段**，正文/思考未被改动。
- **验证**：新增 7 例——exec 通路产 `tool_result`、非 0 退出码标 `is_error`、无输出不产空块、rollout 回执贴到 `tool_use` 之后且剥头、失败回执标 `is_error`、app-server 驼峰输出字段、app-server 失败标错；`pytest tests/` 309 passed、`tests/run.py` 257 tests OK + jsdom 前端渲染通过。

## 4. 非功能需求

- **NF1 零构建前端**：单页 HTML + 原生 JS + WebSocket，免打包。
- **NF2 上下文可控**：编排层只喂对手最新 + 记忆摘要，杜绝隐性 token 膨胀。
- **NF3 隔离可测**：存储层支持环境变量 `AGENTCHAT_CONFIG` 重定向，测试不污染真实数据。
- **NF4 容错**：单轮超时、子进程启动失败、非零退出码均有错误事件上报；**agent 执行失败（API 错误 / 空响应 / resume 异常）时本轮不产出发言、落 system 错误消息并中止会话**——报错信息绝不当议题喂给其他 agent 继续讨论（2026-08-18 修复：曾出现 gemma 报错后错误文本被当发言发给 deepseek、两 agent 基于报错讨论）。**空轮（无正文、无思考、无工具意图，如本地模型空响应）不落空 agent 发言**，仅广播「X 本轮未输出可显示内容，已跳过」提示，避免刷新后记录出现一串空气泡（2026-08-19 修复）。

## 5. 范围与边界

- 不内置模型网关（网关为用户侧基础设施）；但支持 **agent 级 `base_url` 指向任意 Anthropic→OpenAI 翻译网关**（litellm 等），从而让 Claude Code 外壳加载本地模型（见 FR10），且不改 Claude Code 配置、不串默认后端。
- **讨论调性（tone，2026-08-18）**：发起辩论/对话时可选一个讨论风格（16 种：温和/友好/中立/批判/尖锐/激进/唱反调/严谨/审慎/怀疑/务实/数据驱动/学术/简洁/详尽/幽默，或留空自由发挥），每轮 prompt 注入「本场讨论风格：…请始终保持此风格发言」——整场风格一致；tone 随会话持久化，续接历史保持同调。
  - **对抗互动型风格的生效时机（2026-09-15）**：唱反调 / 批判 / 尖锐 / 激进 / 怀疑 这 5 种的描述含「对方 / 对立面 / 反方」语义，必须有对方发言才能成立。故在**无交锋对象的立论轮**（本方本场尚无有效发言，且本轮没有可回应的他人发言）不注入其风格描述，改为要求「先完整、鲜明地陈述你方立场与核心论据；不要预先替对方论证，也不要主动否定或削弱己方立场」；自第 2 次发言起照常按该风格正面交锋。**立论轮只属于会话真正第一次开口**：中止后「继续」（resume）时已有前文交锋，被中止者只是重说这一轮，仍按对抗风格（不当作立论轮）；同会话续开新议题同理不算。其余 11 种自我约束型风格（温和/友好/中立/严谨/审慎/务实/数据驱动/学术/简洁/详尽/幽默）与「有无对方」无关，立论轮照常注入；chat 模式（含单 agent 降级）恒按原样注入。
  - 动因（用户 2026-09-15 实测）：tone=唱反调 且议题「世界是不是有神」时，role=「你坚信世界是神创造的」的**第一个发言者**开场即自我拆台——「我必须立刻对自己持有的这一信仰进行最严苛的审视」，整段用来论证演化论/苦难如何瓦解神创论；对方随后点评「你比很多无神论者更主动地拆自己的台」。原因是 prompt 无条件注入该风格，而它场上没有任何对方观点可反驳，唯一能反驳的对象就是自己的立场。
- **LaTeX 渲染（2026-08-19 已落地轻量版，KaTeX 为未来需求）**：模型输出数学符号常用 `$...$` 包裹的 LaTeX 命令（如 `$\neq$`、`$\rightarrow$`）。现前端 `renderLatex` 做**轻量 Unicode 替换**（≈40 常见命令映射为 ≠/→/≥/α/∫ 等，未映射命令保留原样，pre/code 块保护），零依赖离线可用。**未来需求：引入 KaTeX/MathJax 完整渲染**（分数、根号、矩阵等复杂公式），需引入前端依赖（CDN 或本地资源）。

- 共识判定为 `end_discussion` 两阶段工具调用（见 FR5.3a，2026-08-18 已实现）；TERMINATE 关键词检测保留为兜底。
- 记忆为滚动摘要，无语义检索；token 统计：网关已把 Ollama 真实 usage 注入 claude transcript（`stream_options.include_usage` + `message_delta` 回填，外部 UI 工具可读），**app 内前端展示仍为后续迭代项**。
- 会话级持久化落 `<项目>/.agentchat/sessions.json`；旧的单 `history.json` / `memory.md` 已弃用。

## 6. 设计演进（与初版设想的偏差记录）

> 本节用于追溯需求如何随用户反馈收敛，避免「产出偏离需求却不自知」。

**初版设想（PRD + 最初实现）**
- 单一「项目目录 + Team」驱动一场讨论；左栏为 项目 / Team / Agent 树 + 增删改表单，中间为对话流。
- 每个项目只有一份历史（无「会话」概念）。

**关键演进（均由用户明确拍板，非擅自发挥）**
1. **多会话模型（FR8）**：用户指出「同项目应允许开新会话、需会话历史选择列表」→ 引入 session，每项目多条独立会话，中栏为会话列表。
2. **三栏布局 + 项目常驻左栏（FR6）**：用户要求「项目留在侧边栏、点项目在中栏弹会话、列表可整体隐藏、编辑走行内图标，不要把项目放到配置里」。最终定稿为：左栏常驻可折叠（IDEA 图标栏）、点名称导航、✎ 编辑、中栏会话可折叠（有展开入口）。
3. **单 agent 降级（FR3）**：用户指出「Team 仅 1 个 agent 时轮次无意义、等于自己跟自己辩论」→ 降级单 agent 模式，轮次置灰。
4. **目录服务端选择器（FR1）**：用户要求项目目录弹文件夹选择器而非手输绝对路径 → 新增 `GET /api/fs` 目录树选择器。
5. **配置三层作用域（FR1）**：用户纠正「`max_rounds` 不该挂在 agent 上」「`timeout` 没必要 per-agent、应做成 App 全局设置」→ 轮次移到会话级、超时移到全局 `settings`。
6. **单 agent 真·对话模式 + 全局设置界面入口（FR3/FR4/FR6，2026-08-10）**：用户指出「单 agent 要退回对话模式，但现在不能用——不知道从哪输入、点介入没反应、点『继续会话』语义不对」「全局设置要能在界面操作」。据此定稿：
   - 单 agent 走 `chat` 模式：一次发送 = 用户一条 + agent 一条，可无限续；输入区只留输入框 + 「发送」，辩论控件隐藏。
   - 用户消息（任务 / 对话 / 介入）统一落库 + 回显，此前**只存 agent 回复、用户说的话刷新即消失**的行为按 bug 修掉。
   - 「继续会话」按钮语义改为按模式区分：对话模式=「发送」，辩论模式=「开始讨论 / 继续讨论（已有 N 条）」。
   - 控制指令（停止/暂停/继续/介入）在无运行会话或对话模式下必须返回明确 error，不再静默。
   - 左栏补「⚙ 设置」入口（含折叠图标栏），全局设置不再只能手改 JSON。
   - 顺带修出两个真 bug：① `pause()` 用 `Event.set()+wait()`，事件已 set 时 `wait()` 立即返回 → **暂停一直是失效的**，改为 `resume_event` 反向语义；② 辩论模式的初始任务从不入库。

7. **重建会话时间线与顺序正确性（2026-08-25 修复）**：用户发现重开会话后，abort 缺口轮的 agent 发言排到「会话结束」系统消息**之后**、且**无时间戳**。根因：`orchestrator.py` 在 API-error 时故意不落 agent 最后一轮（防报错文本被当发言），本地在 abort 处留缺口；`reconcile_agent_messages` 的「数量不一致」分支把缺失轮 `msgs.append` 到数组**末尾**，且追加 dict 无 `ts` 字段 → 缺口被补到末尾 + 无时间。修复：reconcile 回填 claude 原生 timestamp（UTC ISO 转本地 `%Y-%m-%d %H:%M:%S`，与 messages.ts 同格式）；并在每 agent 对账后按 ts **稳定排序兜底**，把缺失轮归位到正确时序（顺带重排 `round`）。前端本就按数组顺序渲染、不排序，故顺序错完全源于存储层。治本后重开会话带真实时间且顺序正确；历史缺 ts 的 agent 轮已从 claude 补回，human/system 旧缺口做前向填充兜底。回归测试 `tests/test_reconcile_ts_order.py`。

8. **Agent 类型下拉可真正切换（FR2，2026-09-11 修复）**：用户反馈「新建 agent 时类型只能选 Claude Code，选了 codex/fake 会自动变回 claude-code」。根因在 `frontend/index.html` 的 `openAgentForm().sync`：切换类型时用**原始实体 `a.type`** 作比较基准，新建时 `a` 为空 → 基准恒为 `'claude-code'`，故选 codex/fake 时判定为「已变化」→ 调 `openAgentForm(a)` 重渲染，而 `a` 为空又渲染回默认 `claude-code`，形成弹回；编辑已有 agent 时同样无法改类型；且重渲染会顺手清空已填的 name/role。修复：比较基准改为**本表单渲染时的 `curType`**；切换时传 `agentDraft(a, newType)` 重渲染（携带当前已填值 + 目标类型，编辑态保留 id），既正确切换字段组（claude-code 的「模型来源」↔ codex/fake 的「模型」）又不丢输入；「删除」按钮改为仅在 `a.id` 存在（编辑态）时显示。回归测试 `tests/test_agent_type_switch.js`。

9. **codex agent 可用性（FR2，2026-09-11 修复）**：用户反馈「换 codex 试验五子棋，codex 不能用、不通」。真实落库报错（`www/aitest/test3` 会话）为 `退出码 1: Not inside a trusted directory and --skip-git-repo-check was not specified.`。**两个独立 bug**：
   - **① 缺 `--skip-git-repo-check`**：`_run_codex` 原先拼 `codex exec --json`，而 codex 默认拒绝在「非 git 仓库、且不在 `~/.codex/config.toml` 受信项目列表（`[projects."..."] trust_level = "trusted"`）」的目录运行，直接退出码 1。本 app 的项目目录由用户任选、不可能都预先受信，故**默认带上该 flag**——对应 claude 侧 `--dangerously-skip-permissions`，codex 侧原先漏了这层豁免。命令拼装同时抽成 `_codex_cmd()`（对齐 `_claude_cmd()`，便于测试）。
   - **② `_codex_text` 认不出 codex 0.146.1 的真实事件结构**：实测 `codex exec --json` 只发 4 类事件——`thread.started`（带 `thread_id`）、`turn.started`、`item.completed`（文本在 **`item.text`**，`item.type=agent_message`）、`turn.completed`（带 usage）。原实现只认顶层 `text` / `message.content` / `delta.text`，**不认 `item.text`** → 提取为空 → 界面无输出。**只修 ① 会出现「codex 跑起来但一声不吭」**，故两者必须同修。`command_execution` 类 item 无 `text`，不应被当发言输出。
   - 回归测试 `tests/test_codex_parse.py`（10 项，含 2026-09-11 真实抓取的 codex 事件原文样本，避免被后续版本改结构坑到）；端到端已在原必挂目录 `www/aitest/test3` 实测：退出码 0、解析出完整发言、`thread_id` 抓取正确。
   - 排查教训：曾据「WorkBuddy 托管 node 是 arm64、而 codex 只装了 x64 原生包」误判为 root cause，实为**拿自己 shell 的现象当 app 的证据**；app 进程实际解析到 x64 node，codex 正常启动并返回了自己的报错。**定因果必须用 app 落库的真实报错**（对应用户级 MEMORY 第 11 条）。

10. **codex agent 的工具能力：`end_discussion` 打通（FR5.3a，2026-09-11）**：用户要求「codex 也要支持工具，至少支持我们 agent 的 `end_discussion`，claude 已经实现的」。claude 侧靠项目级 `.mcp.json` 注册 MCP，codex 无该项目级机制 → 改用 `-c` 逐次注入配置覆盖，复用同一个 MCP 脚本；并发现两个非显然的必要条件：
   - **审批模式**：`default_tools_approval_mode` 默认（及其 `auto` 值）在 `codex exec` 非交互场景下**没有审批人**，MCP 调用被自动取消（`user cancelled MCP tool call`），工具形同不存在；必须设 `"approve"`。合法取值（`auto/prompt/writes/approve`）不是靠猜——**给 codex 喂一个非法值，它会在报错里枚举出全部合法变体**，这是查 codex 配置枚举最快的办法。
   - **事件映射**：codex 的 MCP 调用事件是 `item.completed` + `item.type="mcp_tool_call"`（字段 `server/tool/arguments/result/error/status`），与 claude 的 `tool_use` 结构完全不同，必须在 executor 里映射成同一种内部事件 `("tool_use", {...})`，否则**编排层的终止状态机收不到 codex 的票**（现象：codex 能正常对话、但永远不会投终止票，讨论只能靠轮数耗尽收敛）。
   - 端到端实测（用 app 自己的 `_codex_cmd`）：codex 成功加载 MCP 工具 → 调用完成（`status: completed`）→ `reason` 原样回传 → 解析出 `tool_use`。回归测试 `tests/test_codex_parse.py`（17 项，事件样本为真实抓取原文）。
   - 遗留：codex 仍拿不到 shell 工具（其沙箱在嵌套沙箱环境里无法应用策略，见 §7 使用说明）；`codex` 侧模型能看到全部内置工具（未像 claude 那样经网关裁剪到只剩 `end_discussion`），靠 prompt 约束。
   - **工具可达性实测（2026-09-11）**：codex **不把 MCP 工具直接列进工具列表**，而是藏在「工具搜索」后面（`tool_search_call` → `tool_search_output.tools`；模型推理原文："I don't have that tool listed. Let me search for it with tool_search"）。实测 6 个全新 codex 线程里 5 个首次搜索即找到并真调用、1 个没调（也未走文本兜底）——**存在抖动但不高**；两个 codex 一好一坏的现场，根因是**其中一方没重新搜索**（沿用了上一局「工具不在列表」的旧结论），而上一局跑在**未注入 MCP 的旧后端**上、搜索当然为空。**消除搜索的两个配置都不可用**：`features.tool_search_always_defer_mcp_tools=false` 会让工具重复注册、上游报 `Duplicate namespace name 'mcp__terminate_signal'`；`features.tool_search=false` 搜索照样发生。结论：保持现状，靠编排层文本 json 兜底覆盖抖动。

11. **codex 历史重建修复 + 思考展示（FR9/FR11，2026-09-11）**：查「codex 为什么没有思考内容」时顺带发现 `_parse_codex_transcript` 对 codex 0.146.1 的 rollout **解析出 0 个回合**——它按旧的 `o["message"]` / `o["role"]=="assistant"`（chat-completions 风格）取内容，而真实结构全在 **`payload`** 下（`{"type":"response_item","payload":{...}}` / `{"type":"event_msg","payload":{...}}`）。**即 codex agent 的历史重建（reconcile）此前完全失效**，重开会话恢复不了 codex 历史。修复要点：
   - `_codex_iter_payloads` 统一按 payload 取内容（老格式无 payload 时退回整行，兼容早期版本）；
   - 回合切分按 `message/role=user`；`reasoning` → 思考、`message(assistant).content[].output_text` → 正文、`function_call` → tool_use（`arguments` 是 JSON 字符串，需解析）；
   - **`event_msg/agent_message` 与 response_item 的 assistant message 内容重复**，按文本去重，避免正文被拼两遍；
   - ⚠️ **`event_msg/user_message` 的 `message` 也是字符串**（是用户提示词不是正文）——按「message 为字符串即正文」处理会把整段提示词混进正文（实现中踩到并已加回归断言）；
   - 复用 `_normalize_claude_blocks` 产出与 claude 同一套时间线块（thinking/text/tool_use），前后端无需第二套 schema。
   - 实测：两个真实 rollout 从「0 回合」变为 6 / 4 个回合，内容与界面历史一致、blocks 顺序原生、c2 那个真调用工具的回合带出 `tool_use` 块。回归测试 `tests/test_codex_parse.py` 扩至 25 项；后端全量 **210 passed**。

12. **claude 改真流式（FR11，2026-09-11）**：用户问「codex 内容是一下出来的，桌面端却是流式」→ 排查中发现 **claude 侧其实也不是真流式**：`claude --output-format stream-json` 默认只发整块 assistant 消息（实测零 delta），界面上的"逐字效果"是 `_replay` 演的。加 `--include-partial-messages` 即得真增量（实测 72 text_delta + 53 thinking_delta）。改动：
   - `_claude_cmd` 加 `--include-partial-messages`；旧版本不认该 flag 时 `_run_claude` 自愈降级（关掉 flag + 换新 session id 重试一次）。
   - `_parse_claude_line` 解包 `stream_event`（**delta 包在 `{"type":"stream_event","event":{…}}` 里**，不解包读不到顶层 `delta`）。
   - **去重（关键）**：开 partial 后同一段内容会既以 delta 到达、又出现在最终整块 assistant 消息里 → 以 `runtime._streamed_text/_streamed_think` 记账、`message_start` 复位，解析整块时跳过已流式吐过的正文/思考；**但 tool_use 必须仍从整块消息取**（delta 里的 `input_json_delta` 只有半截 JSON，不能流到编排层）。
   - 实测端到端：**69 条 text 事件（最长 3 字符）+ 152 条 thinking 事件**，合计 100 字、无重复。回归测试 `tests/test_claude_stream.py`（11 项）；后端全量 **221 passed**。
   - 对照结论：**claude 有开关可开、codex `exec` 连开关都没有**（codex 真流式已换 `codex app-server`，见 FR12；`codex exec` 保留为自动兜底）。

   15. **「中止 / 继续」定为独立功能（FR4.1，2026-09-14）**：用户先问「暂停是做什么用的，继续讨论不是需要输入才能继续吗」——澄清后发现既有「暂停/停止」**只在轮边界生效**（当前发言必须跑完），对「模型死循环」这一真实场景完全无效；而两个既有「继续」又有三重歧义（解暂停 / 需输入的新一轮 / 会话续接）。用户据此定调：**「中止」与「继续」是与既有几个都不同的能力，做成单独的功能、互不干扰**。据此定稿：turn 级中断 + 被中止的 agent 重新发言（作废半轮落盘留痕、不计轮次/不喂他人）、复用主按钮槽位（生成中=中止、待续接=继续）、原 ctrl 行「继续」改名「恢复」。用户同时纠正了两处我的初版方案：① 不能把「中止」并进「停止」（会丢真中断能力）；② 不能删掉「暂停」那对按钮。
