# 开发文档 · Agent CLI Orchestrator

## 1. 技术栈

- 后端：Python 3.13 + FastAPI + Uvicorn + WebSockets（标准库 `asyncio` 子进程）。
- 前端：单页 HTML + 原生 JS + WebSocket（**零构建**，无 npm 打包）。
- 存储：JSON 文件（`data/config.json`），记忆落项目目录 `.agentchat/`。
- 测试：标准库 `unittest` + FastAPI `TestClient`（需 `httpx`）。

## 3. 数据流

Session 启动时按 `len(agents)` 自动分两种模式：`single = len(agents) < 2`，
`mode = "chat"（单 agent，人机对话）/ "debate"（≥2 agent，轮次辩论）`。

```
浏览器(WebSocket)
   │  action=start {project_id, team_id, session_id, task, max_rounds?}
   ▼
main.handle_start ──► 解析 project/team/agents/session ──► Session(...)
   │                   guard: if session.running → error "正在运行..." 并返回
   │                                                      │
   │   if mode == "chat":                                 │  if mode == "debate":
   │     _chat_turn(task)                                 │     _debate(initial_task)
   │       └ 首条播系统提示(not history)                   │       loop round_i < max_rounds * len(agents):  # max_rounds=每个agent发言次数（N轮=共N×agent数次发言）
   │       └ 有文本 → _record_human(text,"用户")           │         current = agents[round_i % len]
   │       └ _run_turn(一次)                              │         prompt = 身份 + 对手上一句(delta) + 注入   │         (不播「会话结束」，前端仅刷中栏)              │         runtime = runtimes[current]  # 持续 CLI 会话（1:1）
   │                                                      │         runtime.run(prompt, cwd, timeout, meta)
   │                                                      │            │  async generator (text|error|done)
   │                                                      │            ▼
   │                                                      │       broadcast(token/turn_start/turn_end)
   │                                                      │       append_message + 首次创建则 set_agent_session_id
   │                                                      │       检测收敛(end_discussion 两阶段状态机，见 §6；TERMINATE 关键词兜底) / inject / stop / pause
   │                                                      │         └ end_discussion 提议+对方确认 且 round_i >= 2*N-1 才收敛；TERMINATE 关键词兜底
   │                                                      │       broadcast「会话结束」+ run_end mode="debate"
   ▼
broadcast(event) ──► 所有 WS 客户端实时渲染（run_end 恢复主按钮 + 刷新会话列表）
```

暂停语义用 `resume_event`（`asyncio.Event`，默认 set = 未暂停）：
- `pause()` 清除事件 → 循环 `if self.paused: await resume_event.wait()` 在回合边界阻塞；
- `resume()` 置位 → 解除阻塞继续下一轮；`stop()` 同时置位，避免残留阻塞。
（旧实现用 `pause_event.set()+wait()`，已 set 时 `wait()` 立即返回 → 暂停形同虚设，已修复。）

## 4. 关键模块说明

### 4.1 executor.AgentRuntime（状态式 CLI 会话）
- 每个 agent 在某一 app 会话内的「持续 CLI 会话」运行时；编排器持有一个 `runtimes: {agent_name: AgentRuntime}` 字典，同一 app 会话恒定复用，故 agent CLI 会话持续续接。
- `run(prompt, cwd, timeout, meta)` 异步生成器，产出 `(kind, text)`，`kind ∈ {"text","error","done"}`。
- `cli_session_id`：该 agent 的持续 CLI 会话 id；`None` = 尚未开过。
  - **claude-code**：首次 `--session-id <uuid>` 注册，续接用 `--resume <id>`（claude 2.x 不允许复用 `--session-id`，否则报 `already in use`）；异常锁 / 坏 id 时 executor 自动换新 id 重试（自愈）。确定式、无需解析输出。
  - **codex**：**主路径 `codex app-server`**（JSON-RPC over stdio，`initialize` → `thread/start` 得 `result.thread.id` 即 `cli_session_id` → 多次 `turn/start`，逐 `item/agentMessage/delta` 真流式；详见 §6 对应条 + `需求文档.md` FR12）。持久长连接跨本会话多轮复用，跨进程恢复用 `thread/resume`（**实测可用**，需前一个进程优雅退出以落盘 rollout）。握手失败自动回退兜底路径 `codex exec --json`：首次从 JSONL 抓 `session_id`，后续 `codex exec --json resume <id> <prompt>`（codex 不支持自命名 id，`session_id` 抓取为尽力而为，依赖 codex 版本事件字段）。
  - **子进程回收纪律（2026-09-14）**：`codex` 是「node 壳 → 原生 app-server」两层，spawn 一律 `start_new_session=True` + `_kill_proc_group()` **整组**回收（先 `killpg(SIGTERM)` 让 rollout 落盘、超时再 `SIGKILL`；校验 `pgid != 自身 pgid` 防误杀本服务）。只杀壳会留下 PPID=1 的孤儿原生进程，且 rollout 未落盘会让下一条消息 resume 报 `no rollout found`、**静默丢模型记忆**。
  - **fake**：`_run_fake` 纯内存确定性文本，维护自身 `_fake_history` 模拟「有状态会话」；第 `fake_terminate_round` 轮（含）起发结构化 `tool_use(end_discussion)`（不再输出 TERMINATE 文本，见 §6）。
- `meta`：编排器透传 `{"round_index","max_rounds"}`，供 fake 判定收敛轮次。

### 4.2 orchestrator.Session
- 构造：`Session(project_path, session_id, agents, max_rounds, broadcast, timeout)`，从 `read_session` 取历史；按 `len(agents)` 设 `single` / `mode`；从会话读回 `agent_sessions` 映射，构建 `runtimes = {a.name: AgentRuntime(a, agent_sessions.get(a.name))}`（**点历史会话即恢复对应 agent CLI 会话**）。
- 状态：`stop_event` / `resume_event`（暂停语义，见 §3）/ `inject_queue` / `runtimes` / `agent_sessions`。
- `_record_human(text, role)`：统一把用户/任务/人工介入以 `speaker="human"` 落库并广播 `human`（`role` 传前端区分「用户 / 任务 / 人工介入」），刷新后可见自己说过的话。
- `_record_system(msg)`：结论性系统消息（终止原因 / 会话结束）以 `speaker="system"` 落库并广播 `system`。**必须落库**，否则辩论模式 `run_end` 重载（前端 250ms 后从磁盘重载）会把实时系统消息冲掉、刷新即丢失。过程性提示（会话开始 / 暂停 / 继续）仍用 `_emit` 只广播不落库，避免污染「首条 human 即任务」语义与首轮判定。前端 `renderHistoryEntry` 对 `speaker=="system"` 渲染为「系统」气泡。
- `_run_turn(agent, round_i, inject)`：取 `runtime = self.runtimes[agent.name]`；`first_turn = (round_i == 0 and not self.single)`；`runtime.run(prompt, ...)` 流式产出；落 `append_message`；**首次创建 CLI 会话后 `set_agent_session_id` 持久化 `cli_session_id`**（resume 后续不变）。
- `_chat_turn(text)`：对话模式，仅首条(`not self.history`)播系统提示；有文本则 `_record_human(text,"用户")`；跑一次 `_run_turn`（用户本轮消息作为 `inject` delta 发给 agent）；广播 `run_end mode="chat"`（**不播「会话结束」**）。
- `_debate(initial_task)`：辩论模式，任务非空则 `_record_human(initial_task.strip(),"任务")`；`while round_i < max_rounds * len(agents)`；收敛判定（end_discussion 两阶段确认，TERMINATE 关键词兜底，见 §6）；`inject_queue` 取出后 `_record_human(human,"人工介入")`；结束播「会话结束」+ `run_end mode="debate"`。
- `_build_prompt`（**状态式 delta 路由**，不再搬运整段历史）：
  - 身份行 `你是：{role}` 每轮带（极便宜，防 resume 时角色漂移）。
  - `chat`：只把用户本轮新消息作为 delta 发出（其 CLI 会话已持有完整历史），要求「不要调用 end_discussion 工具（辩论模式专用）」。
  - `debate`：把「本方上次发言后的全部他人发言」作为 delta 回传（FR5.3b 已实现；`round_i==0` 时跳过——那是上一场残骸，避免续开新议题混入场）；`inject`（任务 / 人工介入）即本轮新议题；每轮提示词都含**「共识终止」条件**（引导 agent 调用 `end_discussion(reason)` 工具表达终止、不输出 TERMINATE 文本，并明确「至少两轮完整往返才会考虑结束」「调用后还需多数 agent 确认」）——已移除「首轮判定不可讨论即终止」的诱导指令（其会导致第二个 agent 一轮就腰斩整场）。**任务背景补齐（2026-08-21）**：任务只在 round0 经 inject 传给第一个 agent，其他 agent 首轮若只看到 delta 可能无法推断议题（象棋实测：d1 首轮直接走棋「炮8平5」不复述任务，d2 把 CLI 系统提示的技能列表误当议题编出「代码仓库管理」总结并误调 end_discussion；deepseek 急于中止疑同因）。故每个 agent「就当前议题首次发言」（history 中该 agent 最近发言早于最后一条 human「任务」消息）时补注入 `任务背景（本场议题）`，非首轮不再重复搬运。
- 收敛判定（仅 debate，已升级为 end_discussion 两阶段，见 §6）：主通道 = 结构化 `tool_use(end_discussion)`——MCP 服务做最小轮数 gate（`round_i < 2*N-1` 返回 isError）与两阶段确认（提议+对方确认），编排层检测 `terminate_confirm` 后收敛、`reason` 作结论经 `set_discussion_conclusion` 存盘（**仅供前端展示，不回灌 agent——状态式 agent 自身已记住**），系统提示为「双方通过 end_discussion 达成一致，会话收敛。结论：…」。兜底 = 独立一行 `TERMINATE` 关键词（`round_i >= 2*N-1` 才生效，其余当普通文本）。

### 4.3 store
- 所有读写经 `_load()/_save()`，文件为 `AGENTCHAT_CONFIG` 环境变量指向的 JSON（默认 `data/config.json`）。
- 配置/资源持久化在 `config.json`；会话持久化在每个项目目录 `<project_path>/.agentchat/sessions.json`（数组，每项一条会话含 `messages` / `agent_sessions` / `conclusion`）。
- **agent 持续会话映射**：`get_agent_sessions(project_path, sid)` 返回 `{agent_name: cli_session_id}`；`set_agent_session_id(...)` 在首次创建 CLI 会话时写入。点历史会话时编排器据此 `--resume` 恢复对应 agent 会话（1:1 持续会话的核心落点）。
- **提示词日志**：`prompt_log_dir(project_path)/<sid>.jsonl`，每行一条 `{round, agent, role, first_turn, ts, prompt}`；函数 `append_prompt_log` / `read_prompt_log`。编排器在 `_run_turn` 构造完 prompt 后即写入（仅记录、失败静默）。
- 会话函数：`list_sessions` / `read_session` / `create_session` / `append_message` / `get_agent_sessions` / `set_agent_session_id` / `set_discussion_conclusion` / `get_discussion_context` / `delete_session`。
- 提示词日志接口：`GET /api/session/{pid}/{sid}/prompts` 返回该会话全部 prompt 记录。
- `GET /api/session/{pid}/{sid}` 返回会话详情，含 `messages` 与 `agent_sessions`（前端打开会话时自动展示各 agent 的持续会话 id）。

### 让某个 agent 加载本地模型（走 Claude Code 外壳，不串默认后端）
Claude Code 只说 Anthropic Messages 格式，本地模型（Ollama/vLLM/llama.cpp）只说 OpenAI 格式，中间必须有一个翻译网关。推荐 **litellm**，它同时暴露 Anthropic 兼容的 `/v1/messages`，可直接做 `ANTHROPIC_BASE_URL`。

1. 跑网关（用户侧基础设施，本系统不内置）：
   ```bash
   # litellm_config.yaml 节选：把 ollama/gemma 暴露给 Anthropic 格式调用方
   model_list:
     - model_name: ollama/gemma        # claude 侧 --model 填这个
       litellm_params:
         model: ollama/gemma
         api_base: http://localhost:11434   # Ollama 的 OpenAI 接口
   litellm --config litellm_config.yaml     # 默认监听 :4000，提供 Anthropic 兼容端点
   ```
2. 在 agent-chat 的 agent 表单填：
   - 类型 = `Claude Code`
   - 模型 = `ollama/gemma`
   - 模型网关地址 = `http://localhost:4000`
   - 网关 Key = 留空（运行时补 dummy，litellm 放行）
3. 保存后该 agent 拉起 claude 时即注入 `ANTHROPIC_BASE_URL=http://localhost:4000`，所有请求走 litellm→Ollama/gemma，**不动 Claude Code 配置、不串全局默认后端**。链路：`claude → litellm(:4000, Anthropic 格式) → 翻译为 OpenAI → ollama/gemma(:11434)`。

### 中止 / 继续（turn 级中断，2026-09-14 已实现；需求见 需求文档 FR4.1）
「暂停/停止只在轮边界生效」（当前发言必须跑完）对模型死循环无效，故新增 turn 级中断。三层能力互不干扰：

1. ✅ **executor 层：`AgentRuntime.interrupt()`**（协议优先、硬停兜底）
   - **codex app-server**：记录当前 turn id（`turn/start` 应答的 `result.turn.id`，或 `turn/started` 通知的 `params.turn.id`；`turn/completed` 时清空），发 `turn/interrupt{threadId,turnId}`。实测毫秒级生效，且长连接与 thread 保留，续接可复用同一会话。
   - **claude**：`_stream_subprocess(keep_stdin=True)` 保住 stdin，写 `control_request{request_id, request:{subtype:interrupt, cancel_queued:true}}`。**两个配套改动缺一不可**：① `_user_frame` 结尾补 `\n`——stream-json 输入按行解析，原先靠 EOF 断行，stdin 不关就永远等这一行；② 读循环按 `result` 事件主动收尾（`_is_claude_turn_end`）——stdin 不关时 claude 收到 result 也不退出，否则生成器永久阻塞；收尾后主动关 stdin 让进程正常退出（SIGKILL 会残留会话锁）。
   - **兜底**：codex exec 路径无协议通道 → `_kill_proc_group` 整组硬停；协议帧发出后 2.5s 仍未收尾 → 看门狗 `hard_kill()`。
   - 实测（`/tmp/probe_interrupt_raw.py` 对照实验，deepseek-v4-flash：A 不中断 = 4457 字/29.3s/exit 0；B 正文开始 8s 后写中断帧 = 2279 字、**中断→收尾 0.01s**、result `error_during_execution`、exit 1）；中断后 `--resume` 同一 session 实测可用（exit 0，且 claude 自己记得「刚写到第四节被切断」）。
   - ⚠️ 环境坑：`_claude_env` 继承进程环境，若宿主 shell 带 `HTTP(S)_PROXY`，claude 到本机网关的请求会被代理劫持（表现：网关日志里完全没有请求、claude 侧反复 `api_retry 502`）。真实运行（用户直接启动服务）无此问题。
2. ✅ **orchestrator 层：作废半轮 + 精确续接**
   - `Session.abort()`：置 `_abort_requested`（幂等）→ 调 `runtime.interrupt()` → 记录 `last_abort_channel`；与 `stop_event` **分开**（stop=跑完当前发言不再开下一轮；abort=当场打断且本次发言作废）。
   - `_run_turn`：流结束后先判 `_abort_requested`，命中则 `_finish_aborted_turn()`（落盘 `interrupted:true` + 写 `pending_turn` + system 消息）并**在终止状态机之前返回**——半截发言不该产生 end_discussion 投票；同时复位 `_turn_in_flight`（避免看门狗误杀已闲置的 app-server 长连接）。
   - `_debate`：发言被中止即 `break`（不推进 `round_i`、不喂下一位），并以「本场已中止」而非「会话结束」收尾；`run_end` 带 `aborted` 供前端立刻切「继续」态。
   - `start(resume=True)`：从 `pending_turn` 恢复 `round_i` 与发言 agent（**不重置回第一个 agent、不消耗半轮**，轮次预算接着算），注入 `_RESUME_NOTICE`；`start(resume=False)` 会把旧的 `pending_turn` 清掉（新议题顶掉续接）。
   - 单 agent 对话模式的续接**不重复追加用户消息**（agent 侧已有该条）。
3. ✅ **store 层**：`set/get/clear_pending_turn`（session 级字段）。**不从 messages 推导**：一轮的 `round_i` 会因偶发空轮（未落盘的 agent 发言）与「有效发言条数」发生偏移，推导会把续接指到错误的 agent 上，实测值才确定式。对账（`reconcile_agent_messages`）额外加固：保留 `interrupted` 标记、存在中止留痕时不追加（避免 CLI transcript 里的半截再生成一个重复气泡）、不删中止留痕。
4. ✅ **接口层**：WS 新增 `abort` / `resume_turn`（**两种模式都放行**，与 debate-only 的 pause/resume/stop 分开处理）；`GET /api/session/{pid}/{sid}` 增加 `pending_turn`。
5. ✅ **前端**：主按钮槽位三态复用（生成中=「中止」、有待续接=「继续（<agent> 重新发言）」、其余=发送/开始讨论/继续讨论）；被中止气泡加 `.interrupted` 灰化 + 「已中止（本次发言作废）」角标（实时 `turn_end.interrupted` 与历史 `entry.interrupted` 共用 `markInterrupted`）；ctrl 行「继续」改名「恢复」（它只是解除暂停）。

### codex 的工具调用条目在两条通路上命名不同（2026-09-15 修复）
`end_discussion` 在 codex 侧的 item 命名**同一份 codex、两条输出通路不一样**，原实现只判下划线 ⇒ app-server（本 app 默认路径）下 **codex 的终止票实时全丢**：

| 通路 | rollout `originator` | `item.type` | 修复前 |
|---|---|---|---|
| **app-server**（默认） | `agentchat` / `source=vscode` | **`mcpToolCall`**（驼峰） | ✗ 与 `mcp_tool_call` 永不相等 |
| exec（`codex exec --json`）/ rollout 回放 | `codex_exec` / `source=exec` | `mcp_tool_call`（下划线） | ✓ |

- **症状**：codex 两轮真调用（rollout 里 `mcp_tool_call_end` 均 `Ok`）一次都没进终止状态机，阈值 `⌊2/2⌋+1=2` 永不满足，辩论**从未收敛**、只能靠轮次耗尽（3×2=6 条）收尾（实测 s_f85043cf）；而落盘消息里能看到 codex 的工具块，是因为**事后**对账读 rollout（走的是下划线那条）补上的——实时与回放两条路的差异掩盖了 bug。
- **修复**：判定收敛到单一谓词 `_is_mcp_tool_item`（`_MCP_TOOL_ITEM_TYPES = ("mcpToolCall","mcp_tool_call")`），`_run_codex_appserver` 的 `item/completed` 与 `_parse_codex_line` 共用，避免再次分叉。仍只认 `item/completed`（started/completed 各发一条，取 completed 才不重复计票）。
- **对照实测**（`/tmp/probe_codex_tool_fix.py`，走本 app 执行器 + 真实 codex，同一 prompt/模型/MCP 注册，仅 `item.type` 判定不同）：修复后 **1 个 `tool_use`（3.3s 到达）**；退回旧判定 **0 个**（226 thinking + 251 text 事件照常，只是票被丢掉）。旧判定仍接受下划线路径，故 0 票同时证明这次走的确实是 app-server 驼峰通路。
- **附带修掉的对账损失**：`reconcile_agent_messages` 原先用 CLI 回合的**空值**覆盖 `tool_calls`/`tool_results`/`blocks`。但空值 ≠「这轮确实没调用」——claude（gemma）走「prompt 文本 json」兜底解析出的 `tool_use` **不在它自己的 transcript 里**（模型把调用写进了正文），覆盖即抹掉留痕（实测 s_f85043cf：claude 的终止提议在气泡里查不到工具块）。现改为 `_merge_tool_info`：CLI 带工具信息才覆盖；CLI 侧无工具块时由 `_merge_tool_blocks` 把本地工具块按相对位置并回时间线。
- **订正一条此前的误判**：曾据单个 transcript（4fe2f681，`tool_use=0`）推断「gemma4:26b 不会产结构化 tool_use」。**该结论错误**——116 份 claude transcript 里有 6 份含真 `tool_use`（全部是 `mcp__terminate-signal__end_discussion`，回执 `result_ok=True`），工具日志里 gemma 也有 `proposed 3 / confirmed 7`。网关自 2026-08-19 起确实转发 `tools`（仅转发 `end_discussion`、去 `mcp__` 前缀、回程还原），claude 侧由 `_ensure_project_mcp` 自动写项目 `.mcp.json` 注册 terminate-signal。那次是模型选择走了文本路径（两条路径并存且 prompt 明确给了兜底写法），不是能力缺失。

### 消息时间线（ts）
- **落盘**：`store.append_message` 对每条消息 `setdefault("ts", _now())`（本地时间 `YYYY-MM-DD HH:MM:SS`）——**human 消息也走此路径，即「人类发送时间」从落盘起被记录**（此前不记时间，导致无法按人类说话时间编排历史）；前端气泡头部（`.who`）显示 ts（有才显示，实时流不显示）。
- **历史回填**：claude transcript 每个事件带 ISO 时间戳（`timestamp`），`backend/backfill_timestamps.py` 据此回填历史消息：**human 只给「成功送达 claude 且有回复」的提问**按内容匹配 transcript user 事件（无回复的提问=claude 根本没收到，如 gemma 冷启/链路失败空跑，时间无从考证、保持无 ts）、agent 回复按内容匹配 assistant 回合（去 `---` 子串匹配，避免模板答案重复时顺序错位；**思考无正文的回合用 thinking 匹配**，如 gemma 只吐思考的场景）；**先清空旧 ts 再重算**（幂等，可修正历史错配——如失败提问误占 transcript 时间）。用法：`python -m backend.backfill_timestamps <project_path> [--backup]`。
- **s_2289e1cf 时间线（终版）**：8-17 用户连发 6 次「你是谁」，仅第 6 次成功（16:11:26 提问 → 16:12:13 回复，gemma 冷启 47 秒）；前 5 次 claude 根本没收到（无回复、无时间戳，空回复条目已删除、不再显示「本轮未输出独立结论」占位）；「你有多少参数」16:15:22→16:15:26（热启 4 秒）；「你的数据是哪天的」17:32:48→17:33:51（又冷启 63 秒）。
